1. Document control and what survives
Revision 0.3 preserves all 57 functional requirements and 14
nonfunctional requirements of v0.2, with their stable identifiers and
original universal safeguards. Where not expressly amended here,
v0.2’s normative requirement text remains in force by incorporation.
This revision is therefore read with v0.2 for unchanged details; it is not
a destructive renumbering or a declaration that unimplemented
features are complete.

The human owner accepted Phase 2’s engineering foundation after
machine qualification; the Gate B human web/browser walkthrough
was not performed and remains deferred. The accepted machine
evidence, code bases, approval history, and protected Contracts remain
authoritative. The later Gate B r2 report names tested commit 6ba66f5;
verify report identity and digest from repository records before
carrying a receipt into the decision register. Do not treat the report’s r2
publication commit as itself the tested revision.

Evidence vocabulary: ACCEPTED_ENGINEERING_FOUNDATION,
MACHINE_VERIFIED, DEFERRED, NOT_RUN, PASSED, FAILED, INCONCLUSIVE,
BLOCKED, and UNKNOWN must not be collapsed into a single green status. A
reviewer agent is not a human reviewer.


1.1 Non-negotiable constitution

  • Human leadership and final Done remain sovereign; ordinary
    preauthorized operations need not generate needless approval
    requests.
  • Exactly one production-code-writing Implementer per repository/
    owned Engineer transaction. No parallel Implementer swarms or
    competing worktrees against one canonical repository.
    Independent read-only advice or review is allowed under bounded
    permissions; optional internal Implementer advice never
    substitutes for mandatory independent challenge.
  • Kernel, Scheduler, and Supervisor enforce typed authority, policy,
    ownership, test freezes, canonical Git changes, effect intent,
    reconciliation, and halts. Neither prompts nor UI routes can
    impersonate them.
  • Agents are disposable; canonical decisions, Work Orders, Work
    Units, Git objects, frozen Contracts, evidence, and human messages
    are durable. A lost response or uncertain effect does not authorize
    blind replay.
  • Model-free CI remains compulsory. Real-provider smoke tests are
    separately authorized, finitely budgeted, and clearly distinguished
    from scripted-role protocol tests.
  • One local operator and a single-host, loopback-first baseline are
    mandatory before enterprise or remote deployment expansion.
    Corporate and personal installations are separate trust domains.
  • Phase 2’s DG-03/DG-04/DG-05 decisions, effect-class safety,
    ownership fencing, and the protected-test amendment protocol
    remain effective.

3. Revised product intent and accessibility
FR-UX-01 — One-entry local control pane (P3.1). Running lockstep
launches or reconnects to the intended authenticated local control
pane from outside the source checkout. It must load useful diagnostics
when the PostgreSQL/application service is unavailable; no operator is
forced to copy ports, variables, tokens or container names for ordinary
startup. No implicit upgrade/migration merely from starting the
launcher.

FR-UX-02 — Host-side management boundary (P3.1–P3.3). A narrow
trusted bootstrap helper and web pane support typed, allowlisted
lifecycle operations, not arbitrary Docker/shell commands. Explicit per-
user authorization, replay resistance, session revocation, exact Host/
Origin protections, negative browser-origin tests, durable outcomes,
path validation and serialized operations are required. Do not grant
the pane Docker socket or unrestricted application database
credentials.
FR-UX-03 — Truthful system/installation UX (P3.2–P3.3). Show
observed installed version, schema compatibility, running state,
missing prerequisites, failures and available recovery actions in plain
language. Start existing compatible services automatically; require
explicit human review for install, upgrade, migration and restore.
Stage/review the replacement; verify backup before migration; detect
database-ahead and interrupted state; preserve operator installation
and qualification evidence.

FR-UX-04 — Nontechnical application shell (P3.4). Home, Projects,
Tasks, Decisions, Activity, Settings and Advanced provide a consistent
keyboard-usable navigation model. Present goals and next actions
before internal engineering jargon; retain discoverable exact technical
evidence. A browser shell must never counterfeit ready, working or
complete states.

FR-UX-05 — Guided project setup (P3.5). A user can name an
initiative, describe its intended outcome, create or select a local
project, accept safe defaults and see accurate setup status without
knowing Git. The internal Repository/Engineer relationship must obey
accepted DG-03 identity and ownership, and no remote repository may
be created or pushed without separately authorized policy.

FR-UX-06 — Work intake and organization (P3.6). A user can create,
inspect, edit and prioritize project tasks, describe acceptance intent
and blockers, and understand dependency/readiness states without
Work Order terminology. A Ticket is not an authorization to execute
code. Stale edits, duplicates and side effects must use durable typed
application operations. A work item can be organized before an
execution-capable Engineer is configured.

FR-UX-07 — Policy and eligibility visibility (P3.7). Human-friendly
Profile choices and advanced effective Profile identity/version/digest,
immutable gates and exceptions. Display priority distinct from
eligibility; higher-priority blocked work remains blocked. No
dropdown silently weakens immutable universal requirements.

FR-UX-08 — Browser human decisions (P3.8). Show authenticated
decision requests with source, subject, evidence, allowed actions,
expected revision and consequences. Apply exact legal typed
commands with idempotent durable receipts, rejecting stale, replayed
or agent-originated authorizations. No faux approvals for an engine
not yet executable.
FR-UX-09 — Evidence, errors and recovery (P3.9). Activity and
evidence projection from canonical data, with honest PASSED, ATTESTED,
FAILED, BLOCKED, UNKNOWN, INCONCLUSIVE, and NOT_RUN distinctions; raw
artifact access and meaningful remediation guidance. Browser
disconnect or restart must not misstate durable state.

FR-UX-10 — Usability qualification (P3.10–P3.11). Actual browser
tests plus owner review and real nontechnical participant test. A
successful automated Chromium run is not evidence that a real novice
succeeded. Record assistance, confusion, incomplete trials and reasons;
no simulation of human studies.

NFR-15 — First-use comprehension. An operator unfamiliar with Git,
Docker, PostgreSQL or model orchestration can launch, set up, create a
project and task, inspect blockers, and perform supported decisions
through the UI; internal commands are not required for the ordinary
path.

NFR-16 — Local bootstrap least privilege. The bootstrap plane is
usable without application readiness, but only a narrowly
authenticated user-context helper can perform allowed host lifecycle
effects. Protect against local web-origin forgery, forged/replayed helper
messages, XSS credential extraction, symlink traversal, concurrent
management requests, and malicious input.

NFR-17 — Controlled startup latency and upgrade. No gratuitous
reinstall, migration, test suite or provider call on ordinary launch.
Longer user-authorized operations show truthful state and preserve
diagnostic/recovery records after browser disconnect.

NFR-18 — Release usability and accessibility. Browser navigation,
focus, labels, text state, narrow screens and keyboard alternatives are
acceptance properties. Human participant observations are preserved
separately from machine qualification.

C-UX acceptance scenarios (P3.11)

 • UX-C1: One invocation of lockstep opens the intended pane
   through the default browser, with the application database absent
   or stopped.
 • UX-C2: An ordinary returning launch connects without
   unnecessary rebuild/migrate; honest startup failures remain
   inspectable.
 • UX-C3: The UI completes a compatible installation and an
   authorized backed-up upgrade; fault-injected backup, migration,
   crash and database-ahead paths fail closed.
 • UX-C4: A novice creates or imports a project with correct
   repository ownership and no surprise external publication.
 • UX-C5: A task can be created, edited, prioritized, blocked/unblocked
   under policy, and viewed after restart.
 • UX-C6: An authorized human decision applies once; stale request,
   duplicate submission and forged cross-origin authorization are
   refused.
 • UX-C7: Evidence UI matches persisted ledger and shows
   meaningful uncertainty, human attestation and not-run status.
  • UX-C8: The owner conducts and records the formerly deferred
    Gate B browser review against the appropriate installed tested
    application.
  • UX-C9: Real nontechnical users complete defined first-run
    journeys; all assistance and non-completions are recorded.


C-EXEC minimum useful local coding scenario

The human selects one existing repository and authorized bug Ticket
from the UI. Lockstep chooses the effective Bug Profile, creates a
bounded source-linked Contract, independently challenges candidate
tests before freeze, freezes protected tests, runs one Implementer
against confined allowed paths, verifies real compilation/tests and Git
state, performs an independent read-only review and semantic
challenge, commits only through Supervisor authority, and exposes the
exact evidence and human Done choice. Fault injection proves safe
recovery without duplicate mutation. No remote push, PR, Shortcut,
multi-repo, or full Master Plan is required.

A model-free suite is required, using scripted role adapters against
real PostgreSQL, subprocess/Git and effect boundaries. Real provider
CLI capability and model quality require a separately authorized, finite
dogfood trial before saying Lockstep performs real human-equivalent
coding work. Do not call simulated success a real model
demonstration.


6. Critical path and permitted deferrals
The urgent product objective is to get Lockstep useful on one local
repository, not finish optional provider, deployment, Skills or
workplace integrations first. Complete P3’s UI-first control-plane core,
then the C-EXEC engine and live provider proof. P3.1 must not
metastasize into a generalized deployment platform. P3.3 safe install/
upgrade is required for Gate C-UX but its implementation should reuse
Phase 1/2 scripts and tested primitives behind an allowlisted authority
boundary rather than introduce a second orchestration kernel.

Nontechnical usability remains a product acceptance obligation; a thin
initial vertical slice is an engineering checkpoint within Phase 3, not a
false acceptance of the entire Gate C. If the owner later chooses to
advance C-EXEC while some non-safety UI polish is still unfinished,
record a named, explicit gate deferral; do not silently waive security,
persistence or evidence prerequisites.

8. Design gates and authority
Existing DG-01–13 retain their original decisions and statuses.
DG-03/04/05 were accepted in Phase 2; DG-06/07 remain relevant to C-
EXEC and cannot be casually waived; DG-08–12 remain gated at their
respective later scopes; optional DG-13 Mercury research is not on the
critical path.

DG-15 (P3.1 local bootstrap) is the owner-approved amended P3.1
design: single-use fragment-based sign-in, origin-scoped non-cookie
bearer session, strict Host/Origin and XSS controls, temporary
coexistence with frozen cookie pages, a containerized pane without
unrestricted DB/Docker authority, and an authenticated allowlisted
host-user helper. Consentful PATH installation, compatible automatic
start, explicit upgrade/migrate decisions and first-party P3.1 JavaScript
are part of that decision. It authorizes only P3.1, not the whole future
deployment plane.

DG-16 (Phase 3 browser-managed effects) requires verified helper
protocol and authorization, privilege separation, operation locks,
durable results and no host shell command injection. A new UI route
doesn’t create an exemption from the original DG-04 effect guarantees.

DG-17 (Phase 4 live coding) requires concrete agent process
confinement, provider CLI permissions, secrets separation, model
family adapter and real Git boundary verification. This is a hard
precondition to live consequential work, not a later UX enhancement.

Human decisions and qualified read-only reviewer reports must be
distinguished. Approval of a design/Contract is not a receipt for
executing it.
