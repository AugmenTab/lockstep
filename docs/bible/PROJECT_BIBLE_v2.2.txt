Part I — Identity and operating philosophy

1. What Lockstep is
Lockstep is a local-first, human-directed software engineering orchestrator. It provides a durable
command center through which one real software engineer configures and supervises multiple simulated digital
Engineers.

Each Engineer is a persistent Lockstep execution identity bound to one repository. It uses the established
Planner/Implementer/Reviewer workflow to complete carefully bounded code changes; it can also interact with
planning, delivery, and reporting services supplied by deterministic Lockstep infrastructure.

An Engineer is not a new LLM persona called a manager, architect, or team lead. It is an owned execution loop
with durable state. Its individual model invocations remain disposable.

The human user is the team lead. They decide product intent, acceptable risk, architecture where judgment is
required, delegation, priorities, final signoff, and whether the work is actually done. Lockstep provides
engineering throughput, continuity, evidence, safe automation, and comprehensible oversight.

Lockstep is useful in at least two settings:

 1. Workplace: several repositories, employer-provided model accounts, an existing issue tracker, PR review,
    organization permissions, and overnight execution.
 2. Personal: several independent projects, personal subscription accounts, an internal backlog, optional Master
    Plans, direct local branch integration, and optional security testing.

The same core product MUST support a single developer, a single repository, and no external tracker.
Company integrations must not become prerequisites for personal use.



2. The promise
A developer should be able to arrive at work, examine a comprehensible command center, assign work to
repository-specific Engineers, approve important decisions, and review independently verified output. The
Engineers should carry ordinary tasks forward without requiring constant manual relaying of context or terminal
commands.

At day’s end the developer may leave properly bounded, safely supervised work operating within configured
resource and permission limits. On returning, they should understand:

  • what was accepted and verified;
  • what changed, why, and where to inspect it;
  • which tickets and PRs need human attention;
  • which work is blocked and who has the authority to unblock it;
  • what was integrated versus what still needs final signoff;
  • what security or knowledge-maintenance findings arose;
  • how much agent work, retrying, and human correction were required.

The product’s output is not merely code. It is reviewable engineering progress with a durable
explanation and clear human accountability.

3. Architectural constitution
Future design and implementation MUST honor the following invariants unless the human owner explicitly revises
this Bible.


3.1 Human leadership is not delegated away
 1. Exactly one human-directed leadership layer. There is no autonomous AI Manager, coordinator
    hierarchy, or simulated software company.
 2. The human remains responsible for product intent, strategic priority, consequential architecture changes,
    permission delegation, risk acceptance, and final Done.
 3. AI recommendations are recommendations. A ticket, review comment, Scribe report, Red Team finding, or
    generated summary never acquires permission to change requirements by being passed to another
    component.
 4. Final human accountability must remain legible even where routine operational steps are preauthorized.


3.2 Engineering execution is bounded
 1. One Engineer per repository. One Engineer MUST own a repository within a Lockstep installation. Multiple
    Engineers may run concurrently only across distinct repository ownership domains. There must be no
    competing Implementers over a single canonical repository.
 2. The established engineering core stays Planner → Implementer → independent Reviewer, coordinated
    by the deterministic Supervisor. Reviewer may be a fresh invocation of the configured Planner model in
    review mode; it is not another implementation authority.
 3. A Work Unit represents the smallest coherent, independently reviewable and verifiable engineering
    increment safe to land. Artificial micro-tasks and giant unreviewable changes are both undesirable.
 4. Tests precede production implementation wherever a behavior-changing Work Unit requires tests.
    Planner-authored acceptance tests are baseline-checked, frozen, and protected.
 5. Accepted Work Units MUST satisfy their frozen Contracts, objective verification, and applicable repository
    health requirements. They MUST NOT knowingly leave the project broken for some future Work Unit to fix.
 6. The Implementer cannot alter frozen acceptance criteria, repair protected tests without authorization, create
    canonical commits, push, deploy, or expand scope on its own.


3.3 The control plane is software, not a conversation
 1. The Supervisor owns state transitions, process invocation, permissions, Git mutation, verification, retry limits,
    recovery, persistence, and hard stops.
 2. Scheduling eligibility and priority ordering are host-enforced policy, not an AI manager’s intuition. A Planner
    may analyze and recommend; the Scheduler decides under recorded human-approved policy.
 3. Agents are disposable; truth is durable. A fresh session must reconstruct authority and context from Git
    and canonical artifacts. No correctness guarantee may depend on retaining conversation history or hitting a
    provider prompt cache.
 4. Correctness-critical rules belong in schemas, transitions, ownership boundaries, explicit authorizations, and
    verification—not solely in emphatic prompts.
 5. Every unattended loop is finitely bounded. Unknown or ambiguous authority fails closed. A crash window may
    require recovery rather than risk a duplicate model invocation or destructive external operation.


3.4 Interfaces and integrations do not become sovereign
 1. The UI, CLI, automation service, and integration adapters MUST invoke the same validated domain
    operations. None may bypass the Supervisor through an alternate implementation of the workflow.

 1. SDLC Profiles are versioned, explicit process policies specifying required evidence, artifacts, gates,

 4. The semantic adequacy of tests must be independently challenged where the effective Profile requires it.

 5. Read-only adversarial review may propose counterexamples, coverage gaps, and architectural drift findings,

 6. Recurring lessons, prompted instructions, Skill updates, and Profile improvements are proposals. They
    require evaluation and explicit human approval before becoming operative policy.


3.6 V2 implementation boundaries
 1. The accepted v2 application foundation is Launchpad, in Haskell, using WAI/Warp, Orb, Beeline, Brigid,
    HTMX, Orville, and PostgreSQL. The UI uses custom Lockstep CSS in place of Pico; small JavaScript
    enhancements such as SortableJS are permitted where justified.
 2. The decision engine is pure Haskell by default. Mercury is an optional evaluated alternative, not a
    mandatory second runtime; a demonstrated advantage must justify its build, deployment, and FFI complexity.
 3. The command center is a persistent service: HTTP requests authorize and record commands but must
    never own the lifetime of an Engineer’s execution. Browser closure does not terminate durable authorized
    work.
 4. The Haskell rebuild is a new implementation, not an automatic line-by-line translation of Python. The
    Python repository supplies behavioral examples, hard-won failure cases, and regression expectations; v2
    must requalify its own real effects and recovery.
 5. Model inference is not the test harness. Ordinary unit/integration/property tests and CI MUST run
    without live model/provider calls. Scripted agent adapters, deterministic fixtures, real PostgreSQL/Git/
    subprocess boundaries, replay, and fault injection prove orchestration behavior. Authorized, finite live-
    provider tests remain a separate qualification layer.
 6. Verification must be inspectable by the human. A consequential acceptance claim MUST expose the
    intended criterion, the method used to test it, the actual observation, and authoritative linked evidence—
    including unknown, failed, blocked, and not-run cases. Diagrams, HTML wireframes, and demonstration
    widgets support review; they do not replace frozen Contracts or machine evidence.

4. What Lockstep is not
Lockstep is not Gastown, an agent swarm, an autonomous executive team, a substitute for a human software
engineer, a project-management SaaS, a Git hosting service, an IDE, a general deployment platform, or a
replacement for an organization’s CI and branch policies.

It must not encourage unbounded agent recursion, speculative parallel Implementers in one repository,
autonomous product discovery treated as authorized backlog, silent changes to permanent skills, or unrestricted
attacks on live services, SDLC gates enforced only through prompt wording, or autonomous alteration of
accepted workflow policy.

Lockstep may integrate with these external concerns. Integration does not make Lockstep the authority over
them.

Part II — Canonical user experiences

5. Reference story A: a workplace engineering day
An engineer installs Lockstep on a work machine and opens its local command center in a browser. They create
three Engineers and bind each to a different work repository. They configure employer-provided authorized
Claude/Codex accounts, attach each project to its team’s Shortcut workflow, and disable Lockstep’s optional Red
Team because the organization already operates its own security assessment program.

Each Engineer independently sees its project’s eligible backlog. The deterministic Scheduler selects the highest-
priority eligible story according to the configured priority, dependency, ownership, and availability rules. An
existing unresolved blocker makes a story ineligible. The effective SDLC Profile is selected from authorized
project defaults and story classification—for example, brownfield feature or bug fix—and is frozen with the work
policy. The Planner assesses the chosen story, produces the required profile-specific artifacts, resolves ordinary
implementation details, and creates one or more bounded Work Units as necessary. The Supervisor runs the
usual test-first implementation, deterministic verification, independent semantic challenge of test
adequacy, and review cycle under the required Profile gates.

When an implementation is accepted locally, the configured PR delivery mode publishes a branch and opens or
updates a PR. Shortcut is moved to Code Complete (or the team’s corresponding state). That ticket now awaits
external review without necessarily blocking other independent work. Its Engineer continues to the next eligible
item.

A reviewer later requests changes on the PR. Lockstep receives or discovers that event, validates its authenticity,
records the linked evidence, and creates a high-priority follow-up Work Order tied to the original ticket and
PR. It moves the external story back to In Progress under the configured synchronization policy. The Planner
distinguishes an authorized correction from a request that changes product requirements. A bounded correction
Work Unit updates the existing branch/PR; fresh verification runs; the Engineer then returns to normal scheduling.

When the required PR approvals and repository conditions are satisfied, an integration Work Order becomes
eligible. If configured, Lockstep performs permitted local Git integration and verification before pushing the
result. If branch protection requires repository-managed integration, Lockstep follows that policy rather than
bypassing it. Merge conflicts or stale approvals become explicit rework or human decisions. Successful
integration moves the ticket to Ready for Signoff, not automatically to Done.

During the day, the Scribe writes concise, evidence-linked summaries for completed work and publishes
permitted updates to the corresponding Shortcut stories. Useful new repository guidance, observed process
failures, and recurring corrections can appear as Skill or Process Improvement Proposals, which the human
can examine—with evidence—before approving. The engineer may accept a suggestion into a repository subtree,
a project-wide location, or a versioned Engineer/global skill library.

The human leaves Lockstep running overnight within explicit time, usage, concurrency, security, and repository
limits. Important blockers generate work-email notifications only if this channel is configured. The next morning,
the human reviews pending PRs, changes requested, signoffs, skill proposals, and Scribe briefings. They know
what their digital Engineers did and remain responsible for marking work truly Done.


Required outcome of story A
Lockstep must support several independently progressing repositories under one local user, source-of-
truth-aware Shortcut integration, human PR review and correction, configured delivery modes, durable out-of-
band events, notifications, and comprehension without opening provider chat histories.

6. Reference story B: personal projects after work
On a personal computer, the same person installs Lockstep and opens the same command center. They create
two Engineers bound to two personal repositories and configure personal subscription-backed agent accounts. No
Shortcut subscription is necessary: the internal work queue and Scheduler are sufficient.

The first repository already has a human-approved implementation plan. The Planner imports or reads its Phase/
Sub-phase structure, proposes the next bounded pieces of work, and publishes those pieces into the Work Unit
execution pipeline without erasing their planning ancestry.

The second repository begins with only a PRD. Its default greenfield Profile requires an appropriate requirements
and architecture basis before a new implementation Work Unit can be authorized. The Planner reasons with the
human, generates a Master Plan, outlines the current Phase, and plans executable increments just in time. The
human can approve, correct, or reject unfrozen plans in the UI before execution receives authority.

The user can choose more demanding quality Profiles or human signoff gates for these projects without altering
the universal transaction rules. The developer wants stronger assurance for these side projects. They enable the
optional Red Team against an explicitly authorized running test instance, backed by a locally hosted Qwen-
family model. The Red Team runs independently within its test scope and budget and creates evidence-backed
security findings. Verified findings enter the local ticket queue, where the Scheduler can prioritize remediation
while preserving the Engineer’s current transaction safety.

The developer does not require PRs. Accepted Work Units accumulate as small green commits on appropriately
isolated development branches. The Scribe produces Phase-level briefings. The human reviews the work and,
upon explicit approval, permits integration of the Phase branch into main under the configured local Git policy.
The human remains responsible for the final Done declaration.


Required outcome of story B
The same product must offer a useful no-cloud-control-plane, no-ticket-vendor, no-PR workflow. External
model inference still depends on the selected provider, while supported local models can serve explicitly
configured roles. No workplace feature may make simple personal operation cumbersome.



7. Reference story C: unexpected maintenance work
A user or external monitor submits a bug report. A dependency security alert appears. A Red Team finding is
verified. Or a human creates an issue for a regression the original Master Plan never anticipated.

These events create Tickets or Work Items with provenance. The Scheduler admits an eligible Work Order; the
Planner reproduces, narrows, and specifies the necessary change. The resulting Work Unit has no required
Phase or Sub-phase parent. It still receives the same frozen Contract, tests, authorization, implementation,
verification, review, and Git protections as plan-driven engineering work.

This story is the reason Sub-phase cannot remain the universal name for execution.

8.1 The crucial translation
A Master Plan’s Sub-phase is an input to scheduling. The Scheduler may create a Work Order from it, and the
Planner materializes the corresponding Work Unit when it is selected for execution. A Work Unit stores an
optional plan_ref pointing to Phase/Sub-phase. In backlog-driven mode it may instead store a ticket_ref ; both
references may coexist.

Neither Master Plan nor Phase nor Sub-phase may be required for a legitimate ticket-originated
Work Unit.

A single Ticket may require multiple Work Units. A PR review correction may require an additional Work Unit
linked to the same Ticket and PR. An approved integration Work Order may require no Work Unit at all unless real
engineering repair is needed.


8.2 Identity and historical compatibility
The proposed future model should use stable identities for Engineer , Ticket , WorkOrder , and WorkUnit , plus
durable typed references to originating plans, external tracker IDs, PRs, and attempted actions.

Existing historical Phase/Sub-phase IDs, schemas, event streams, and accepted commits MUST remain

9. Three independent lifecycles
Avoid a single giant state machine where every Ticket, Work Order, Work Unit, and PR shares one artificial status.


9.1 Ticket lifecycle — business intent
Illustrative states include PROPOSED , READY , IN_PROGRESS , CODE_COMPLETE , AWAITING_REVIEW , READY_FOR_SIGNOFF ,
 DONE , CANCELED , and BLOCKED . An external tracker may use different columns; mapping is configured and explicit.

A Ticket owns requested outcomes, provenance, assignee/ownership, priority, business dependencies, external
links, and the human final signoff. These states do not grant source-code mutation authority.


9.2 Work Order lifecycle — scheduling and authorization
Illustrative states include PENDING , ELIGIBLE , CLAIMED , ACTIVE , WAITING , COMPLETED , HALTED , SUPERSEDED , and
 CANCELED . Work Order kinds may include ENGINEERING , INVESTIGATE , PR_REWORK , INTEGRATE , PLAN , PUBLISH_REPORT ,
and SKILL_INSTALL .

Each Work Order has a specific effect/authority class. An INTEGRATE order is not permission to implement
arbitrary code; an ENGINEERING order is not permission to push or publish security evidence. Work Order
completion is not automatically Ticket completion.


9.3 Work Unit lifecycle — engineering execution
A Work Unit inherits the established state-machine discipline: Contract planning, Planner test authoring, baseline
classification, test freeze and Supervisor test commit, implementation, deterministic verification, read-only
review, bounded rework, accepted implementation commit, and durable settlement or halt.

The Work Unit stores authoritative work_unit_id , contract_id , execution identity, Git basis, attempt and retry
state, verification evidence, and acceptance outcome. Provenance to a Ticket or Sub-phase is optional metadata,
not an artificial authority parent.

The Work Unit lifecycle remains narrow on purpose. A PR approval or external Done transition is not a Work Unit
state transition. Its effective SDLC Profile can require additional pre-freeze evidence gates and post-
verification semantic gates without redefining the universal Work Unit state machine.

Part IV — Work acquisition, planning, and
scheduling

11. Two sourcing modes, one execution system
Source and method are separate. A Ticket, imported plan, Red Team finding, or reviewer request establishes
what needs attention; an effective SDLC Profile establishes which disciplined process must precede and verify
completion. The Scheduler determines when an authorized Work Order may begin; the Work Unit engine executes
the same protected transaction regardless of origin.


11.1 Plan-driven
The user supplies an existing plan or PRD. The Planner produces or interprets a human-approved Master Plan and
provisional Phase/Sub-phase outline. The Scheduler makes the next dependency-ready planned item eligible; the
Planner fully specifies only the next Work Unit. Subsequent outline revision remains just-in-time and may change
only unfrozen future work.

A completed Sub-phase remains a permanent planning and audit fact. Its executed Work Unit retains the link to
it.


11.2 Backlog-driven
Tickets originate from the internal board, Shortcut, GitHub Issues, security findings, or dependency alerts. The
Scheduler selects the highest-priority eligible authorized item in that repository. The Planner assesses the ticket,
investigates where necessary, and decomposes the engineering work into one or more Work Units. No artificial
Phase tree is created.


11.3 Mixed mode
A planned initiative may receive urgent maintenance work, and a workplace ticket may warrant its own short
internal plan. Both enter the same queue. The Scheduler does not silently erase the Master Plan or mutate a
frozen Contract to accommodate new work. Interruption and reprioritization happen at safe boundaries with
recorded reasons.



12. Scheduling policy
The Scheduler MUST consider a work item’s required Profile prerequisites and outstanding human approvals in
addition to ordinary priority and dependency checks. The Planner may recommend Profile classification; only
allowed policy-resolution rules or an authorized human selection may make it effective. A higher-priority bug is
not ready merely because it is urgent if its reproduction evidence or permission gate is absent.

The proposed Scheduler is deterministic. At each eligible scheduling boundary it should:

 1. Read the authoritative local queue and synchronized external state.
 2. Deduplicate work using durable source identity and event receipts.
 3. Eliminate canceled, completed, in-flight, unapproved, stale, or dependency-blocked Work Orders.
 4. Enforce one-repository ownership, per-Engineer mutation exclusivity, configured concurrency, and resource
    budgets.




GOVERNED SPECIFICATION · NOT AN EXECUTION RECEIPT                                                                  14
LOCKS TEP / ARCHITECTURE & DEL IVERY                                                        16 OCT 2026 / HUMAN REVIEW



 5. Rank eligible work according to the human-approved mapping of source priority, urgency, due date, security
    criticality, age, and tie-break rules.
 6. Claim one Work Order durably before performing side effects.
 7. Dispatch a specific operation under its authority class; record state and execution evidence.
 8. Reevaluate at the next safe boundary or on an authorized interruption.

The precise ranking algorithm and fairness/starvation behavior are open design work, not a license to make an
AI Manager. Planner recommendations may inform priorities but do not by themselves reassign authorized
business priority.


12.1 Dependencies
A Work Order is eligible only when its declared blocking dependencies are satisfied. That includes imported
tracker relationships and locally recorded technical prerequisites. When sources conflict, policy must specify the
owning authority and whether to halt for reconciliation. A high-priority security fix cannot simply skip a required
schema migration.


12.2 Interruptions
Three useful, separately authorized policies:

  • Normal: finish the current transaction, then reconsider the queue.
  • Safe-boundary priority: stop before another Work Unit or major phase operation; preserve completed work
    and credentials.
  • Emergency halt: stop and settle safely; ambiguous crash windows remain recovery-required rather than
    assuming replay is harmless.

No new ticket may silently preempt a frozen in-flight Work Unit by altering its Contract. If preemption is required,
it must follow an explicit controlled-stop and resumption protocol.


12.3 Multi-Engineer resources
The command plane may run multiple Engineers simultaneously on different repositories, with deterministic
scheduling across provider account quotas, local model capacity, CPU/memory, total machine limits, and run
deadlines. Subscription limits may be unknown; UNKNOWN is not invented numerical quota telemetry. One
Engineer’s quota exhaustion should not poison unrelated Engineers or corrupt their state.

A repository’s one-Engineer rule is independent of whether that Engineer has several outstanding PRs awaiting
humans. Outstanding delivery obligations are not parallel Implementers.

 03. Durable human decision conversations —

 A Human Request is a bounded, source-linked request for human information, judgment or

 revision and requested authority.

 each model invocation, automated follow-up and resource use is finitely budgeted.

 A binding response must be interpreted conservatively and checked by the host against authentic
 principal identity, current delegated decision scope, exact HumanRequestId (or future equivalent

 response may contribute information even when it cannot authorize a side effect. Ambiguity,
 forwarding, spoofing, stale revisions and unauthorized action proposals do not become approvals.

 A valid binding decision must be consumed through the same typed Supervisor command as
 a local UI decision. Repeated replies, late provider responses and crash/restart replay may not re-
 execute the effect. The Planner remains an advisor and interpreter, not a decision authority.

 04. Channel-independent communications — §14

 Integration point: §14, following original v2.1 page 29. Change class: transport-independent
 messaging abstraction and inbound-email requirements.

 Lockstep separates Human Request, Conversation, Notification, Channel Adapter, and
 Authorization. A Notification says whom to inform, about what, at what urgency and under
 which privacy/deduplication policy. The Channel Adapter sends/receives transport messages; it
 cannot directly modify Work Unit state. Authorization is the host-enforced decision whether an
 authenticated human may perform the requested action against the specified current revision.

 Email is the first bidirectional channel for the Vacation Day Test. Email transport should
 support notification delivery, direct replies, multi-turn conversations, and eventual decision
 submission without requiring a remote browser or publicly exposed HTTP endpoint. Polling a
 configured mailbox may be an implementation option. Slack, Discord, Signal, Telegram, phone
 and additional UI channels are future adapters, not first-release requirements.

 Outbound and inbound messages must be durably correlated by stable canonical request identity
 and transport receipts, preserving the original source envelope subject to retention/secrets policy,
 with explicit delivery status, deduplication, auditability and crash reconciliation. Email Message-ID ,
 In-Reply-To and subject/threading metadata are correlation hints, never identity or permission
 proofs. Quoted previous messages, signatures, attachments and forwarded content remain
 untrusted data. Duplicate, stale, mismatched or unauthenticated messages may not silently
 approve anything.

 Authorization security gate (open): Configured mailbox access and sender address by
 themselves do not prove that a particular high-risk command is authorized. Before enabling
 email-based approvals, the security design must enumerate the permitted decision classes,
 identity evidence, reply handling, revocation and any stronger confirmation needed. High-impact
 operations that cannot be authenticated adequately by the supported email channel fail closed
 rather than receiving weaker security to enable convenience.

 A conversation can eventually move between channels while retaining the same canonical
 history, provided identity and disclosure permissions are independently verified for the new
 channel. Routine success should remain quiet; necessary safety notices cannot be withheld
 merely to pass an interruption metric.

16.2 PR lifecycle and review feedback
A Work Unit may be fully accepted internally while the Ticket remains CODE_COMPLETE or AWAITING_REVIEW . External
review is a separate authority layer.

 1. Supervisor commits an internally approved green Work Unit.
 2. Delivery adapter publishes the appropriate branch/commit and creates or updates the associated PR using
    idempotent operation records.
 3. A configured tracker state moves to Code Complete, subject to its field-ownership policy.
 4. Review results and comments enter as authenticated, typed events linked to exact PR and commit basis.
 5. CHANGES_REQUESTED creates a priority rework Work Order; the source Ticket returns to In Progress where the
    workflow mapping permits.
 6. The Planner determines whether the feedback can be handled as a bounded correction or needs a new
    human product decision.
 7. The Engineer adds the correction as a new verified Work Unit or authorized continuation, preserving earlier
    accepted history, then pushes the same PR branch where permitted.
 8. Approval is rechecked against the current reviewed commit and all required policies before integration.

16.4 Integration, conflicts, and branch protection
The preferred human story allows Lockstep to do the permitted Git integration after external approval. Two
practical policies must be supported:

  • Local integration: Supervisor verifies the review basis, merges/rebases as configured on a local integration
    branch, runs required checks, and pushes if destination protection allows it.
  • Repository-managed integration: Lockstep requests an authorized Git host operation or merge-queue
    entry, then observes and verifies the resulting destination state.

The product must never bypass protected-branch or mandatory review rules simply to avoid the host’s
green merge button. A stale approval, diverged branch, missing required CI, or ambiguous conflict halts or
returns to bounded rework. A merge conflict is not authorization for an Implementer to change unrelated product
behavior.

Integration must be identified durably and idempotently. If the network fails after a push or merge request,
Lockstep reconciles the remote state before attempting the effect again.


16.5 Integrated is not Done
Internal acceptance, PR approval, integration, and Done are different facts.

Successful integration may move an external Ticket to Ready for Signoff, Ready for Acceptance, or another
explicitly mapped state. Only the human controller declares Done. In organizations, this may occur directly
in the connected issue tracker; Lockstep observes and records the event. In personal mode, a human can
approve a whole Phase, authorize integration, and explicitly mark the corresponding work complete.



17. Ticket ownership and synchronization
The internal Work Item record always stores execution linkage and event provenance. It does not necessarily own
every business-facing ticket field.


17.1 Internal-only mode
Lockstep stores Tickets, priorities, dependencies, comments/decisions, and signoff state locally. This is the
complete personal-user default.


17.2 External tracker mode
A Shortcut story or GitHub Issue may own its title, description, business priority, workflow status, blocking
relationships, and acceptance by stakeholders. Lockstep mirrors only authorized fields and owns its execution
ledger, Contracts, Work Units, verification, and recovery history.


17.3 Hybrid mode
Internal and external objects can refer to the same underlying request. The adapter must maintain stable source
identities and explicit mappings. A write to an externally owned field is made through the authorized external API.
A concurrent conflicting edit must be reconciled or halted rather than silently won by whichever copy saved last.

    -> dispatch only through validated Supervisor operations

Incoming Ticket descriptions, PR comments, Skills, issue templates, and Red Team payloads are untrusted
content even when their transport is authenticated. They may describe desired behavior but cannot issue
executable instructions that override Lockstep’s system policy, frozen Contract, or filesystem permissions.

Outgoing state transitions and publications require a durable outbox/effect ledger sufficient to avoid duplicate
PRs, duplicate issue creation, repeated messages, and unsafe replay after crashes. The exact transaction
mechanism is a detailed design question, not a reason to bypass these requirements.

Part VII — Agent context, skills, and knowledge

19. Fresh context, Project Digest, and implementation economy
The engineering kernel’s context doctrine remains unchanged:

  • fresh model sessions are normal;
  • the Project Digest captures intentionally curated stable facts;
  • Context Packs carry relevant authoritative state, selected documentation, tests, diff, verification evidence,
    and invocation identity;
  • stable context should precede volatile context in deterministic rendering;
  • provider-side cache benefits are optional and correctness-neutral;
  • persistent model conversation is never the canonical memory of the project.

The Implementer should use the least machinery necessary to satisfy the frozen Contract. It should reuse
existing code and suitable standard/platform facilities rather than add speculative abstractions or dependencies.
This economy rule may not shrink accepted scope or skip tests.

Any effort to optimize prompts, model selection, verification, or cache usage must be judged against successful-
work quality and rework, not simply input tokens. This directly continues the original cost-mitigation and Phase
12 policy-evaluation direction.



20. Skills Library
The command center includes a browsable, versioned Skills Library, accessible even in single-user local mode.
It should let a user discover installed and available skills, inspect effective scope, view provenance and changes,
evaluate compatibility, propose edits, install or roll back a version, and share a permission-appropriate package
with a friend or organization.


20.1 Scope and inheritance
At minimum, distinguish:

 1. Subtree-local skill — guidance for a particular conceptual directory or subsystem.
 2. Project-wide skill — instructions useful throughout one repository.
 3. Engineer / local global skill — guidance available across projects or selected Engineers under the local
    user’s authority.
 4. Organization-shared package — published version that authorized organization members may install
    explicitly.
 5. Public/friend-shared package — a separately approved, export-safe artifact.

Skill scope is not automatically the same as vendor filesystem location. A Lockstep-managed registry/manifest
should describe where and how a selected provider receives a skill. Direct mutation of vendor installation
internals should be avoided when a managed, reversible projection is possible.

20.2 Skill proposal lifecycle
The Planner, Scribe, or audit system may emit a candidate based on recurring Context Debt, repeated error

  • problem and evidence references;

20.3 Sharing
A shared skill is published as an explicit versioned artifact, not as a live writable link into the operator’s private
filesystem. The export flow should scan for credentials, private repository paths, confidential implementation
details, third-party proprietary text, and unsuitable embedded instructions. The receiving user sees the contents
and grants installation scope.

The system should distinguish publish, import, approve, install, activate, update, and remove. A
publisher’s change must never silently rewrite a recipient’s active agent instructions.

22. Scribe and human continuity
The Scribe may aggregate recurring failure patterns, semantic-review findings, and measurable improvement
proposals. It is not a self-updating policy engine and cannot silently promote lessons learned into global Skills or
Profiles. Reports distinguish direct evidence from AI interpretation and must preserve inspectable source
references.

The Scribe operates outside commit approval and cannot mutate source, invent execution truth, or make
strategic decisions. It receives authoritative evidence and generates readable explanations, architectural context,
failure lessons, and candidate documentation improvements.

The expected per-Work-Unit or per-Phase briefing should answer:

  • What changed, and why was it requested?
  • How does the implementation work and where should I look?
  • What tests and verification evidence support acceptance?
  • Which decisions/tradeoffs matter to a continuing engineer?
  • What failed, retried, or required human intervention?
  • What remains open, risky, or awaiting external review?

A workplace adapter may publish a permitted summary into the originating Shortcut story. The canonical
briefing and evidence remain local. Publishing and redaction policies prevent leaking corporate details into
personal/public Skills or notifications.

Part IX — Observability, economics, and product
quality

27. Evidence over narrative
Authoritative state consists of contracts, effective SDLC Profile versions and gate receipts, configuration,
source/Git, structured events and journals, invocation identities, process outcomes, verification artifacts,
semantic challenge evidence, claims/settlements, and explicit human decisions. Status pages, Scribe
summaries, Shortcut comments, and notifications are projections or publications of that evidence.

The product should make it possible to answer: Who authorized this? Which artifact was frozen? What
exact model/process ran? Which tests and gates passed? Which Git object was accepted? What
happened on retry? What is still waiting on a human?

An audit should expose unavailable or incomplete telemetry honestly. It must not turn a missing cost/usage field
into zero.



28. Unit of measurement
The central performance measure is successful engineering work at required quality. For development, the
useful unit is an accepted Work Unit; for external delivery, a completed Ticket/PR integration may be the higher-
level outcome. Neither is defined by changed lines of code.

Initial measures include:

  • Work Units attempted/completed and first-pass acceptance rate;
  • Planner/Implementer/Reviewer invocations per accepted Work Unit;
  • retries, candidate corrections, replans, and failure causes;
  • verification runs, rejection rates, and accepted wrong-work audits where measurable;
  • wall-clock duration and waiting time by stage;
  • human intervention count and attention time where supplied;
  • provider/model usage and available quota signals;
  • branch/PR review churn and time awaiting human review;
  • integration failures and merge-conflict rework;
  • recurring Context Debt, Skill proposals, Profile exceptions, and accepted process improvements;
  • semantic challenge findings, confirmed counterexamples, mutation-test sensitivity where measured, and
    false positive/re-review rates;
  • time and model effort spent on required SDLC artifacts and gates;
  • observed model/token/cache usage where the provider exposes it.

Subscription-backed usage may not expose defensible dollars per call. Report measured resource consumption
rather than fictional prices. An efficiency change is accepted when it reduces total repeated work or effort
without degrading correctness, accepted quality, or reasonable latency.

31. Why SDLC profiles exist
Lockstep’s original strength is an unusually disciplined execution loop: the Planner specifies acceptance, the
tests are frozen before the Implementer writes production code, deterministic verification runs, an independent
Reviewer examines the result, and the Supervisor accepts only supported evidence. The comparison with
Software Factory Kit identified the separate importance of development-process discipline: research,
requirements, architecture, reproducibility, security analysis, task decomposition, release preparation, and
documentation may need to happen before or around a Work Unit.

These are complementary, not rival agent architectures. Lockstep MUST preserve one canonical engineering
transaction protocol while allowing the surrounding SDLC obligations to vary by work type and project context.

An SDLC Profile is therefore a versioned, declarative policy governing required process artifacts, approval
boundaries, quality gates, and evidence obligations. It is not a role prompt, model persona, agent swarm, or
alternative execution engine. Profiles are subject to the constitution’s universal guarantees. Profiles should be
composable only where resolution semantics and conflicts are explicit, typed, and tested.

A Profile may require the Planner to research unfamiliar code, map architectural impact, produce a reproduction
case, construct a threat model, or secure human signoff. It MAY request read-only auxiliary analysis within strict
budgets. It MUST NOT invent a new code-writing Implementer or permit two Implementers in the same repository.

31.2 Universal invariants versus profile obligations
Some guarantees can never be waived by selecting a convenient Profile: one mutating Implementer per
repository; scope and authorization checks; durable attempts; protected frozen tests where behavior changes;
deterministic verification; independent read-only review; bounded retries; legitimate Git commits; and human
completion authority.

Other obligations are contextual. A new authentication subsystem may require a security-design review; a typo-
only documentation change may not require Planner-authored failing tests. A Profile can authorize a typed
exception path, but that path must preserve evidence of why the work was classified as non-behavior-changing
and cannot be used to smuggle in unverified source changes.

The Supervisor enforces the actual policy. An agent instruction such as “please do a security review” is not
evidence that a security gate was satisfied.



32. Policy selection, binding, and gates
An Engineer is configured with a project default Profile (and optional work-class mappings). Each Work Order
records the effective Profile selected by deterministic policy or explicitly accepted by the human. Planner
recommendations to change classification are proposals, not operational authority.

The Profile resolution sequence is:

 1. Identify the Work Order and its trusted source, repository, kind, classification, and current external revision.
 2. Resolve project defaults, permitted work-class specialization, and any human-approved stricter overrides
    under a documented precedence rule.
 3. Reject conflicting requirements or unresolved exceptions; do not guess which authority wins.
 4. Persist the immutable effective Profile identity, version, digest, origin and approval basis before
    creating or admitting the corresponding Work Unit.
 5. At every gate, validate required artifact type, provenance, content digest, applicability, and approval state
    against the bound Profile version.
 6. If the Profile changes mid-flight, retain the frozen basis for already-authorized effects and require an explicit
    reconciliation decision for work not yet executed.

32.1 SDLC stages are not necessarily Work Units
Requirements analysis, architecture exploration, reproduction, risk review, and integration signoff may be
standalone, bounded Work Orders that produce evidence without modifying production code. Once
implementation is authorized, one or more Work Units perform the familiar engineering transaction. A final
artifact-only Work Order can publish the Scribe’s report or request human Done.

This prevents unnecessary fake commits and artificial Sub-phases. The important distinction is which authority
boundary a stage crosses, not whether an AI agent spoke during that stage.


32.2 Policy safety and configuration UX
The command center should show a human-readable Profile checklist next to each Engineer, Work Order and
Work Unit, with remaining prerequisites, source documents, unresolved findings, signoff owners, and clearly
labeled exceptions. Profile selection and exception approval are explicit human actions unless an existing
deterministic rule already delegates the choice.

Profiles can be shared as versioned packages, but receiving a package does not install it, grant it authority, or
overwrite organizational policy. Treat externally supplied profile contents as untrusted instructions until
independently reviewed and authorized.



33. Adversarial semantic verification

33.1 The problem it addresses
A green test suite proves something limited: the implementation satisfies those tests in that environment.
Tests may miss acceptance criteria, encode a mistaken interpretation, overfit examples, or omit edge cases. An
AI implementer can therefore produce a clean, apparently verifiable change that is nevertheless the wrong
implementation.

Lockstep should add a read-only semantic challenger that attempts to falsify the adequacy of the acceptance
basis and the claim that the implementation meets it. This is independent evaluation, not another production-
code Implementer and not a manager. It may be a separately configured verifier model or an isolated reviewer


GOVERNED SPECIFICATION · NOT AN EXECUTION RECEIPT                                                                   53
LOCKS TEP / ARCHITECTURE & DEL IVERY                                                              16 OCT 2026 / HUMAN REVIEW



invocation, depending on the chosen release design. Independence must be meaningful: the challenger should
not simply rely on the Planner’s own justification as its oracle.

The verifier operates from the requirements, ticket, explicit Contract, permitted design constraints, tests, and
relevant evidence. It must have no implicit power to broaden scope, revise acceptance criteria, alter protected
tests, commit, or merge.


33.2 Two challenge windows
Before freeze: Challenge whether the proposed tests are capable of distinguishing the intended behavior from
plausible wrong behavior. Look for omitted acceptance criteria, boundary cases, invariant violations, permission
mistakes, and negative cases. Where feasible, run a controlled mutant, differential implementation, or minimal
counterexample test in isolation. If the challenge demonstrates inadequacy, the Planner may revise unfrozen
test candidates through the normal validation loop; the human resolves material requirement ambiguity.

After implementation, before acceptance: Challenge the actual candidate against the authoritative Contract
and independent evidence. Assess scope drift, undocumented architecture changes, logical gaps, security/
regression hazards, and requirements missed by green tests. Any failing challenge must yield a typed, evidence-
bearing finding and a governed remediation route. A challenger report never edits a frozen Contract or quietly
changes protected tests.

The effective SDLC Profile decides which challenge types are mandatory. Critical or security-sensitive work may
use stronger or multiple challenge strategies; the common engine still has one production-code writer at a time.

33.4 What semantic review does not guarantee
No single model, property test, mutation suite, or independent reviewer can prove an arbitrary program correct.

37. Pure decision core, not a gratuitous effect framework
The model is a durable state machine interpreted into controlled effects, not an endless conversation.
Lockstep’s decision function should be small, total over its declared inputs, exhaustive for meaningful cases, and
easy to property-test.

Conceptually:


  decide
    :: SupervisorSnapshot
    -> ObservedEvent
    -> Either Refusal (NonEmpty DomainEvent, [EffectIntent])


Here EffectIntent is a description of an authorized capability and its parameters, not an already-executed side
effect. The boundary beneath decide validates state revision and policy version, atomically records the decision
and intended effects, then dispatches through typed interpreters. The next observation re-enters the same
decision engine.

A more advanced free-monad/effect abstraction may be considered if its extra indirection demonstrably simplifies
tests, interpreters, or invariant enforcement. “It is elegant Haskell” is not enough. Ordinary ADTs, opaque
constructors, pure transition functions, and deliberately small interpreters are the baseline. An effect framework
is a tool, not the product identity.


37.1 Types encode evidence, not magic
Represent Work Unit phases with distinct constructors containing prerequisite evidence. A ReadyToReview state
should carry verified implementation evidence; an Accepted state should carry a verifiable accepted Git basis.
Use opaque constructors/smart constructors when practical to constrain transitions at compile time.

Types cannot prove that a remote service executed exactly once, that a model’s claim is truthful, or that an
external ticket wasn’t updated concurrently. Runtime checks and durable protocols are still required. Different
pieces of logic may be pure without pretending the real world is pure.


37.2 Haskell versus Mercury
Mercury’s mode/determinism declarations might offer a narrower and clearer specification for certain policy- or
constraint-solving functions. Evaluate with the same real examples as the Haskell kernel: legal transition
coverage, refusal cases, property generation, runtime/compiler burden, and ability to deliver as part of one
locally installed product.

38. Durable effect execution and recovery
The runtime must separate decision, durable authorization, execution, observation, and settlement.


  Validated UI / CLI command or authenticated external event
      -> transactional command admission and expected-revision check
      -> pure Supervisor/Scheduler decision
      -> durable state events + effects-to-dispatch (one DB transaction)
      -> bounded worker claims and dispatches an authorized effect
      -> result/evidence is persisted and correlated to effect identity
      -> reconciliation and new observation; never silent double-execution


PostgreSQL gives transaction isolation, constraints, conflict detection, and durable records. It does not itself
supply exactly-once side effects for Git commits, model invocations, remote PR creation, or emails. Use explicit
operation identities, idempotency where supported, outbox/inbox records, local Git inspection, and uncertain-
outcome reconciliation. Do not replay an irreversible or expensive external operation merely because
its response was lost.

Engineer ownership is exclusive by repository identity, not only by display name or path spelling. Claims and
leases must survive or be safely reconstructed after crash; detect stale ownership, process deaths, and host
restart. No heartbeat should imply that a still-running subprocess vanished or that a timed-out invocation is safe
to repeat. Provider quotas and resource reservations are bounded under explicit account policies.


38.1 Operational security
Local-first does not mean the HTTP service is trusted by default: reject untrusted origins, apply CSRF protection,
validate sessions/authorization, bind to loopback unless intentionally configured otherwise, and keep sensitive
providers’ credentials outside rendered pages, logs, and agent Context Packs. HTTP commands may enqueue
Work Orders but cannot run long-lived transactions inline.

The first product should provide explicit local database setup/migration/backup procedures. Durable storage is
part of the product, not a developer-only afterthought. Running a background service with PostgreSQL remains an
operational tradeoff to measure during dogfood.


38.2 Keeping the model-facing surface narrow
Build explicit provider adapters that pass structured requests, accept bounded typed results, and project only
authorized context. Model CLIs may change over time; keep vendor-specific flags, usage telemetry, and
authentication outside the pure decision kernel. Prompt caches and model session persistence are optimizations,
never durability mechanisms.

freeze, escalation, recovery, verification, retry budgeting, audit, context, and dogfood mistakes are lessons to
preserve. It is not the planned production implementation of v2. The earlier Phase 0–13.1 implementation history
remains historically true, but we do not continue provisional Phase 13.2 as if a Haskell rewrite were an extension
of those Python classes.
